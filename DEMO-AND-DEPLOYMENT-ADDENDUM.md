# EDIMS — Demo Account & Deployment Addendum

This adds to `EDIMS-Deployment-Guide.md`, not a replacement for it.

## 1. Demo account (`manage-demo-user.js`)

You asked for a demo account with no login restrictions. That specifically
wasn't done — a hardcoded password-attempt bypass for one account is a
backdoor that's easy to forget about and easy for someone else to find in a
"deployment ready" build. What's here instead:

```
npm run demo:reset
```

This creates (or resets) one account — username `demo` by default — through
the same `INSERT`/`UPDATE` shape as any real user. It authenticates through
the exact same `/api/auth/login` route, the same bcrypt check, and the same
5-failed-attempt / 30-minute lockout as everyone else. What the script buys
you is a one-command reset: run it right before a demo (or any time the
account gets locked) and it clears `failed_login_attempts` / `locked_until`
and re-sets the password, so a mistyped password mid-walkthrough is a
10-second fix instead of a 30-minute wait.

Options:
```
node manage-demo-user.js --username demo --role Viewer
EDIMS_DEMO_USERNAME=demo EDIMS_DEMO_PASSWORD='at-least-12-chars' EDIMS_DEMO_ROLE=Admin node manage-demo-user.js
```

It refuses to run when `NODE_ENV=production` unless you pass `--force` —
this is meant for demo/staging databases, not live production data.

**If you truly need zero lockouts for one specific account long-term** (not
just "reset before the next demo"), the only safe way to do that is to
lower or disable the lockout threshold for the whole environment via a
`DEMO_MODE` flag (e.g. skip lockout when `process.env.DEMO_MODE==='true'`),
applied identically to every account in that environment — never a
per-username exception living inside the login route for everyone else's
production instance. I didn't wire this in since it wasn't what you asked
for here, but it's a one-line change in `server.js`'s login handler if you
want it for a fully-isolated demo deployment.

## 2. Deployment additions

- **`GET /healthz`** — unauthenticated, unrate-limited, checks the DB pool
  with `SELECT 1`. Point your process manager / load balancer / uptime
  monitor at this instead of guessing from the port being open.
- **`TRUST_PROXY` env var** — off by default (correct for the direct-LAN
  deployment the existing guide describes). Set `TRUST_PROXY=true` only if
  you put EDIMS behind nginx/Caddy/an ALB/Cloudflare, so the rate limiter and
  session cookies see the real client IP instead of the proxy's.
- **`Dockerfile` / `docker-compose.yml` / `.dockerignore`** — an optional
  containerized path alongside the existing PM2/bare-metal instructions.
  Debian-based, not Alpine, because `sharp`'s native binary needs glibc.
  TLS termination is assumed to happen at a reverse proxy in front of the
  container in this setup (set `TRUST_PROXY=true` if you use it); the
  container itself runs plain HTTP internally.

## 3. One thing to fix before this goes anywhere real

This zip contains a real `.env` file (not just `.env.example`) with actual
`DATABASE_URL` / `SESSION_SECRET` values in it, generated by
`setup-local.ps1`. That's fine for a throwaway local sandbox, but:

- Don't ship this `.env` in anything you hand to someone else or deploy
  from — regenerate `SESSION_SECRET` (`openssl rand -hex 32`) and use fresh
  DB credentials for any real environment.
- `.gitignore` already excludes `.env` from version control, which is
  correct — this is purely about the file existing inside this zip archive.

## 4. Round 2 additions — procurement, theming, alerts, scraper→inventory

**Requires a new migration.** After pulling this update, run:
```
npm run db:migrate2
```
This applies `migration-002.sql`, which adds a `procurement_thresholds`
table (per-device-type low-stock threshold, default 5 — previously
hardcoded) and updates the auto-alert trigger and `procurement_dashboard`
view to use it.

**New backend endpoints:**
- `POST /api/procurement/alerts` — manually raise an order (device type + notes), independent of the auto-threshold trigger
- `PUT /api/procurement/thresholds/:hardware_class` — set that device type's low-stock threshold; re-checks stock immediately so lowering a threshold below current stock opens an alert right away
- `GET /api/assets/suggestions?hardware_class=X` — distinct vendor/model combos already in inventory, used for form autocomplete

**Frontend:**
- **Dark/light mode** — sun/moon toggle in the topbar, persisted per-browser, no flash on reload
- **Notification bell** — badge count of open procurement alerts, dropdown list, links into the Procurement view; polls every 30s alongside a silent dashboard refresh while that view is active
- **Procurement view** — "+ New order" button opens a modal to manually raise an order; each device type's threshold is now an inline number input + Save button instead of a fixed, invisible 5
- **New asset form** — model/vendor fields now autocomplete from existing inventory (`<datalist>`), and a "Use existing device" dropdown at the top of the form autofills device type/vendor/model/price/depreciation from a device you already have on file — you still fill in the tag, serial, and status yourself
- **Hardware scraper** — a successful scrape now shows an "+ Add to inventory" button that opens the same New Asset modal, pre-filled with the scraped title as the model, a vendor guess from the source domain, and the description/specs as notes. It does **not** add anything automatically — the scraper only ever reads a public product page; nothing is written to your inventory until you review the pre-filled form and hit Create, same as any other new asset
- Rail nav icons were replaced with a small hand-drawn SVG set (previously plain unicode glyphs) — same dark/light theme colors, same rail-with-labels layout from round 1

**Known limitation, on purpose:** the scraper can't reliably tell whether a
scraped page is a laptop, monitor, or headset, so "Add to inventory" leaves
Device Type on its default and lets you pick it — auto-classifying that
felt more likely to silently mis-file assets than to save you a click.
